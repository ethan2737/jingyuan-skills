# PRD 就绪闸门

本文件定义 `$jingyuan:pm` 何时可以生成或更新 PRD。

## 五步闸门

### 1. 问题验证

必须能回答：

- 这是什么问题？
- 谁遇到这个问题？
- 现在如何解决？
- 当前解决方式的成本是什么？
- 不做这个产品或功能会怎样？

### 2. 术语澄清

必须能回答：

- 核心对象叫什么？
- 角色之间有什么区别？
- 关键状态如何流转？
- 哪些词不能混用？

术语已稳定时，写入或更新 `docs/context.md`。

### 3. 场景压实

每个 Must 功能至少有一个具体场景：

- 角色
- 触发条件
- 用户输入
- 系统响应
- 用户得到的结果
- 失败或异常时的行为

### 4. 范围裁剪

必须明确：

- Must：没有它产品不成立。
- Should：重要但可以后置。
- Could：锦上添花。
- Won't：本期不做。

Won't 内容必须进入 PRD 的“本期不做”；反复出现或容易误加时，写入 `docs/out-of-scope/`。

### 5. 理解确认

写 PRD 前必须输出理解确认摘要：

```markdown
## 理解确认

- 问题定义：
- 目标用户：
- 核心场景：
- MVP 范围：
- 本期不做：
- 关键风险：
- 待确认项：
```

用户确认后才写入 PRD。若用户要求先出草稿，也必须把未确认内容标记为 `[待确认]`。

## 允许先出基线 PRD 的例外

旧项目逆向时，如果已有代码和文档足以形成现状描述，但业务意图仍不完整，可以先出基线 PRD。必须：

- 标明证据来源。
- 区分已实现能力、推测需求、建议补齐、待确认。
- 不把猜测写成事实。
