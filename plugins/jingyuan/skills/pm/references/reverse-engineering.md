# 旧项目逆向指南

本文件只在进入旧项目逆向模式时读取。

## 目标

把“现有实现”翻译为“可执行的产品需求文档”，而不是写一篇代码导读。

## 扫描顺序

按以下顺序读取，减少误判：

1. 文档：`docs/PRD/prd.md`、README、需求文档、设计文档、接口文档、数据库文档。
2. 结构：目录树、入口文件、路由、依赖清单、环境变量、配置文件。
3. 数据：接口定义、数据库 schema、状态管理、缓存、队列、权限模型。
4. 行为：核心页面、关键服务、关键流程代码、表单校验、异常处理。

## 每一步要回答的问题

### 文档层

- 项目对外说自己是什么？
- 是否已有目标用户、业务范围、限制条件？
- 是否存在和代码不一致的描述？

### 结构层

- 这个系统分成哪些模块？
- 入口在哪里？
- 哪些路由或命令是主要使用路径？
- 哪些依赖暗示了鉴权、支付、搜索、AI、消息通知等能力？

### 数据层

- 核心实体是什么？
- 实体之间怎么关联？
- 是否存在角色、权限、状态流转？
- 哪些字段说明了真实业务约束？

### 行为层

- 用户能做哪些关键动作？
- 每个动作的输入、处理、输出是什么？
- 出错时系统怎么处理？
- 哪些逻辑像是产品规则，哪些只是实现细节？

## 输出中间产物

在生成 PRD 前，先整理以下内容：

### 1. 功能清单

建议使用这 5 列：

| 功能 | 当前状态 | 证据来源 | 推测目的 | 备注 |
|------|----------|----------|----------|------|

其中：

- `当前状态`：已实现 / 部分实现 / 疑似存在 / 待确认
- `证据来源`：文档 / 目录 / 配置 / 代码行为 / 用户确认
- `推测目的`：从实现反推出来的业务目标

### 2. 角色与场景

- 角色能从权限、菜单、接口、页面入口、文案中反推。
- 场景能从主路径、导航结构、核心按钮、批处理入口、定时任务中反推。
- 无法确认就写 `[待确认]`。

### 3. 流程

至少整理：

- 一条主流程
- 一条关键异常流程
- 一条高风险边界流程

### 4. 已知问题

把以下问题单独列出，不要混在“需求”里：

- 页面行为和文案冲突
- 配置和实现冲突
- 权限控制不一致
- 缺少异常处理
- 缺少校验
- 功能名义存在但逻辑不完整

### 5. 待确认项

以下内容默认高风险，优先列为 `[待确认]`：

- 角色权限边界
- 计费、结算、审批、状态流转
- 删除、撤销、回滚、幂等规则
- 通知触发条件
- 数据口径与报表定义
- AI 结果的人工审核规则

## 证据写法

反推结论尽量带来源，例如：

- `来源：README`
- `来源：路由结构`
- `来源：package.json 依赖`
- `来源：页面行为`
- `来源：用户确认`

不要贴大段代码，把证据概括到足够支撑判断即可。

## PRD 写法要求

逆向模式下的 PRD 至少分清三层：

1. **产品现状**：现在系统客观具备什么。
2. **推测需求**：为什么当初会这样设计。
3. **建议补齐**：为了让需求完整或后续迭代可控，需要补哪些规则。

如果现状和建议冲突，明确写出来，不要糊成一句空话。

## 禁止事项

- 禁止把实现细节原样复制成需求。
- 禁止把猜测写成事实。
- 禁止只看目录不看行为就下结论。
- 禁止因为“看起来合理”就补完用户角色和商业逻辑。
