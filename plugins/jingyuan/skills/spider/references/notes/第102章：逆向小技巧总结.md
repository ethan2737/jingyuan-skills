**拦截器**

- 网站是否使用拦截器的特点是查看多个请求接口的参数是否都被加密、响应内容是否都被加密；
- 并且加密的数据的特征是否一致，比如是否都符合`md5`或者`base64`等
- 并且在启动器中，看到了`Promise.then`
- 此时，可以猜想网站大概率使用了拦截器
- 可以尝试搜索`interceptors`



**Cookie信息确认**

- 有时候Cookie的内容很多，并不能确定里面的内容哪些是有用的，哪些是无用的，并且是否需要逆向的
- 在application中清空所有Cookie的内容，重新走一遍请求流程
- 再次观察Cookie的内容，此时显示的Cookie内容，就是请求所需要的完整内容



**快速确认函数的参数**

- 在函数调用中，要想快速确认参数的传递逻辑，通过调用栈溯源即可
- 如果一个变量是函数通过传参传递进来的，通过调用栈，找到调用这个函数的地方
- 查看调用函数的参数即可确定



静态数据查看页面源代码，数据直接提现在页面源代码中；动态数据在数据包中，触发接口获取，一般是`JSON`字符串；

如何确定参数是否加密，查看2-3次接口，看加密参数是否变化，变化的是加密的，不变的是固定的。

有的参数是在前端加密的，但是在服务器端有可能是不会检测的，可以先发一次请求，看是否可以返回数据，然后把加密参数注释掉，看是否还依然能返回数据。

通过`xhr`快速定位加密入口的方式：优先看入参，如果入参已经是加密好的数据，中间的代码没必要看；然后看调用栈的方式是通过二分法查看，可以一次跨多个栈，分段定位。

当调用栈中出现`Promise.then`时，表示为是异步调用，如果切换`Promise.then`之前的调用函数，作用域是不会改变的，观察那个蓝色的箭头是不会移动的。如果要看异步代码执行的结果，就需要在异步之后下断点，然后重新触发接口

追栈的时候一定要注意接口的地址是否是目标接口，因为会有很多接口走异步代码

刷新页面和单独触发接口是不一样的，刷新网页会加载很多其他的接口，而重新触发接口只会加载这一个接口，就不会出现请求地址变化的问题

当跟栈的参数出现在一个不确定的函数中时，可以查看入参和返回值的变化，速度判断是否在这个函数进行了加密

抠代码的逻辑：找核心代码，比如要找的是参数如何加密的，那么就直接扣抠直接给参数加密的代码。

在浏览器请求头中看到的信息，有的是`X-Sign`这种首字母是大写的，但是当我们全局搜索的时候确什么都搜索不到，反而是搜索小写字母的`x-sign`可以。是因为源代码是都是小写的，在浏览器中自动转换成了大写的。

要快速确定加密逻辑是否在函数内进行的，先看入参，是否加密，再看返回值是否加密

抓包后看到加密数据的类型，排除hash算法后，大概率是对称加密或者是非对称加密，所以可以搜索`encrypt`、`decrypt`。搜索出的结果比较多，多下断点，看程序走哪里。

在浏览器上复制加密数据是，如果比较长直接复制有可能是复制不完整的，可以在控制台使用`copy(e)`的方式

`postMessage`方法

`window.postMessage`是一种用于在不同的窗口、`iframe`或者标签页之间安全的传递消息的`API`，它可以跨域传递数据。它主要用来解决在同源策略下，不同来源的文档无法直接进行JavaScript交互的问题。`postMessage`方法为跨文档消息传递提供安全的突进。

```javascript
otherWindow.postMessage(message, targetOrigin, [transfer]);
```

`otherwindow`：要发送消息的目标窗口对象，可以是 `window`、`iframe.contentwindow`等
`message`：发送的消息内容。可以是字符串、对象或其他可以序列化的对象。
`targetorigin`：目标窗口的源(协议+域名+端口号)，用于控制消息发送的安全性。值可以是一个具体的域名，例如`https://example.com`或`"*"`，表示不限制域名。
`[transfer]：`可选的`Transferable`对象数组，通常用于转移`ArrayBuffer`或`MessagePort`等接收消息的窗口，例如`iframe`内部的脚本，可以通过监听`message`事件来获取消息。

```javascript
window.addEventListener('message', function(){
    //安全检查，确保消息来源是预期的
    if(event.origin !== "https://xxxx.com"){
        return;
    }
    // 处理消息
    console.log("Received Message:", event.data);
});
```

测试cookie是否需要逆向的方法，将cookie内的全部内容都放在请求中，追一注释掉cookie信息，看是否可能正常获取响应内容。

测试请求头中的内容也是同样的方法

通过在application中cookie信息一栏，HttpOnly字段可以区分是服务器返回的，还是JS代码生成的。打勾的是服务器返回的，没有打勾的是JS生成的，但也不是100%准确。但是在console中输入document.cookie，获取的内容一定是不包含JS代码生成的。

快速判断cookie是服务器返回的还是JS代码生成，可以搜索cookie的值，在搜索结果也中查看是否有`set-cookie`操作，如果有，就是服务器返回的，如果没有就是JS代码生成的。
