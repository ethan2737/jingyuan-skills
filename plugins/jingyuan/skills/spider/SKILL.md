## Crawler Classification

Use this sequence when the user asks "how should I crawl this" or when the target difficulty is unclear:

1. Check page source or initial HTML.
   - Data exists in HTML: use the static page route.
   - Data is missing: inspect DevTools Network, especially Fetch/XHR.
2. Check whether Network has a clear API response.
   - Plain JSON/HTML with stable parameters: use the Ajax/API route.
   - Requires login state, Cookie, Referer, or CSRF token: use the session route.
   - Parameters are encrypted, signed, or generated by JS: use the JS reverse route.
3. Check whether the site needs real browser behavior.
   - Requires clicking, scrolling, frames, canvas, or heavy dynamic rendering: use the Selenium route.
   - Requires `window`, `document`, `navigator`, browser APIs, or many missing globals when running JS in Node/Python: use the environment-emulation route.
4. Check project scale.
   - One-off script or learning demo: keep a small `requests`/Selenium script.
   - Multi-page, multi-spider, pipelines, middleware, proxy, or distributed crawling: use the Scrapy route.

## Reverse Debugging Evidence

For JS reverse engineering, signature analysis, anti-debugging, webpack, WASM, RPC, or browser environment emulation, treat browser DevTools evidence as required. Do not pretend a CLI-only workflow can see runtime-only values, call stacks, live cookies, breakpoints, or browser API behavior.

Use browser automation when available and appropriate:

1. Open the target page in a real browser.
2. Inspect Network Fetch/XHR requests, request method, URL, headers, cookies, payload, and response.
3. Inspect Initiator, Sources, pretty-printed JS, breakpoints, watch values, and call stack.
4. Export or copy the smallest useful artifacts into the answer or working files before analyzing.

Do not use automation as a shortcut when the page requires the user's private account, captcha solving, payment, identity verification, or actions the user has not authorized. In those cases, guide the user to provide evidence step by step.

When browser automation or CLI extraction is not possible, ask for one small artifact at a time in this order:

1. Target URL and the exact data or request that needs reproducing.
2. A copied `curl` command from DevTools Network, with secrets redacted if needed.
3. Request headers, query parameters, form payload, and response sample.
4. The names of suspicious fields such as `sign`, `token`, `params`, `encSecKey`, `m`, `data`, or `callback`.
5. The Initiator stack or screenshot showing which JS file triggered the request.
6. Relevant pretty-printed JS snippets around encryption, interceptor, hook target, or debugger statement.
7. Runtime errors from Node/Python execution, especially missing globals such as `window`, `document`, `navigator`, `location`, `crypto`, `localStorage`, or canvas APIs.

After each artifact, reassess the route. Stop asking for more information once the next debugging step is clear.

## Route Output Format

When giving a crawling plan, answer in this order:

1. Classification: name the route and why.
2. Evidence to collect: HTML, Network request, headers, payload, response, Initiator, cookies, JS call stack, or runtime errors.
3. Minimal implementation path: the simplest toolchain that should work.
4. Relevant chapters: list only the chapters to read next.
5. Similar cases: cite matching entries from `references/case-index.md` when useful.
6. Safety and tests: rate limit, secret handling, parser/request-builder tests, and live-site caveats.

## Safety And Quality

- Treat copied cookies, tokens, passwords, proxy credentials, and account identifiers as secrets. The bundled note copies were sanitized, but generated examples must use placeholders such as `<COOKIE>` or environment variables.
- Treat `E:\Project\Spider` case code as unsanitized source material. Read it selectively, redact secrets, and avoid copying brittle headers or old cookies.
- Do not recommend bypassing access controls, abusing authenticated sessions, or scraping private data without authorization.
- Prefer rate limits, caching, pagination controls, and incremental storage to reduce load and improve performance.
- For SQL examples, use parameterized queries. For Redis/Mongo/MySQL credentials, use environment variables or local config placeholders.
- Mention that third-party site layouts, APIs, browser drivers, and anti-bot behavior may change; verify current behavior with DevTools or official docs when the answer depends on a live service.
