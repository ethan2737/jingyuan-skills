# Vertical Slice 开发切片

JingYuan 的开发计划和实现优先按端到端可验证切片组织，而不是按数据库、API、UI、测试的水平层分批。

## 定义

一个 vertical slice 是一条窄而完整的用户或系统行为路径。它通常覆盖必要的 UI、API、数据、状态、错误处理、测试和 smoke 验证。

## 好切片

- 有明确触发入口。
- 有可观察结果。
- 能 demo、自动测试或手动验证。
- 完成后产品能力增加，而不是只多一层基础代码。
- 涉及层次可以很少，但必须闭环。

## 坏切片

- 只创建所有数据库表。
- 只写所有 API。
- 只画所有 UI。
- 只搭完整架构但没有可用行为。
- 只添加文件但无法证明用户或系统行为改变。

## Tracer Bullet

基础设施可以存在，但必须尽快接上第一个 tracer bullet：
- 最小页面能触发一次真实状态变化。
- 最小 API 能完成一次真实请求和响应。
- 最小 CLI 能执行一个真实命令并输出可断言结果。
- 最小数据路径能写入并读回一条真实记录。

基础设施 Phase 若没有 tracer bullet，必须标为 `Spike`，不能标为功能完成。

## dev-plan 规则

每个 Phase/Slice 必须写：
- `切片类型`：`AFK`、`HITL`、`Spike`、`QA`。
- `Blocked by`：前置 slice 或 `None`。
- `可验证行为`：触发、路径、结果。
- `涉及层次`：UI、API、数据、状态、外部依赖、测试。
- `公开接口 / seam`：实现和测试入口。
- `测试意图`：要覆盖的行为，不写内部实现细节。
- `验证命令`：真实命令或手动 smoke 步骤。
- `NOT in scope`：明确不做什么。

## dev-builder 规则

每个 Task 开始前确认：
- 当前 Task 对应哪个可验证行为。
- 公开 seam 是什么。
- 是否默认 TDD；如果不走 TDD，替代证据是什么。
- 需要修改哪些文件，是否会 scope drift。

每个 Task 完成后确认：
- 行为已验证，不只是编译通过。
- checkbox 已更新。
- review 已完成且未 stale。
- 验证证据是当前代码修改后的新鲜证据。

## AFK / HITL

- `AFK`：上下文完整、风险可控、可自动验证，Agent 可独立推进。
- `HITL`：需要用户判断、账号权限、设计确认、架构取舍或范围裁剪。
- `Spike`：用于消除技术不确定性，必须产出结论、风险和后续建议。
- `QA`：以验证、浏览器检查、回归或 smoke harness 为主要产物。
