# Testing Policy

测试要证明公开行为，不证明私有实现。

## 默认策略

- 新业务逻辑、bugfix、复杂状态流、外部集成：默认 TDD。
- 纯视觉微调、简单配置、脚手架初始化：可以使用编译、截图、接口 smoke 或手动 checklist 替代 TDD，但必须说明原因。
- 没有合适测试 seam 时，记录为架构问题；不能用测试私有方法或内部调用次数制造假信心。
- 实现前记录目标行为的关键公共 seam；回归任务同时记录当前可观察行为。只有 seam 存在多种合理选择、跨系统边界或选择代价显著时才请求确认，不为明确的小任务增加人工门禁。

## TDD 循环

1. 写一个失败测试，只覆盖一个公开行为。
2. 运行目标测试，确认失败原因就是预期行为缺失。
3. 写最小实现，只让当前测试通过。
4. 重新运行目标测试，确认通过。
5. 绿灯后再重构。
6. 重构只整理当前 slice 内的命名、重复和结构，不引入新行为或无关架构调整；随后重新运行目标测试。

## 测试边界

应测试：
- 用户或系统触发的可观察结果。
- 公共 API、CLI 命令、页面交互、服务接口、持久化结果。
- Happy path、error path、empty/loading state、关键回归。

不应测试：
- 私有函数。
- 内部调用次数。
- 自己控制的内部模块 mock。
- 与用户行为无关的实现细节。
- 用与实现相同的算法重新计算 expected。预期结果必须来自规格、已知字面值、经人工或独立系统核验的固定样例，或独立 oracle；不得直接采集待测实现输出，否则测试可能按构造必然通过。

Mock 只用于系统边界：
- 外部 API。
- 时间。
- 随机数。
- 文件系统。
- 网络。
- 必要时数据库或进程边界。

## 验证命令

计划中应为每个 slice 写出项目适用命令，例如：
- 类型检查。
- 单测或目标测试。
- 构建。
- lint。
- 浏览器或接口 smoke。
- 安全扫描。

命令必须使用目标项目真实脚本名，不写泛泛的“运行测试”。
