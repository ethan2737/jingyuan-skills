# Diagnostics Loop

Bug 和性能问题必须先建立反馈循环，再修改代码。

## Bug 修复

1. 定义症状：用户看到什么、系统输出什么、期望是什么。
2. 建立可信失败信号：实际运行一个测试、命令、接口请求、浏览器步骤或日志检查，确认它精确命中用户症状、修复前能重复呈现失败、修复后可用同一路径判定转绿、尽量确定且 Agent 可执行；记录命令或步骤与关键失败输出。
3. 非确定问题先用重复、并发、压力或时间窗控制提高复现率，再逐项删除输入、操作、环境和依赖；直到每个剩余条件都对失败不可缺少。
4. 列出 3-5 个可证伪假设，按可能性和区分能力排序；每个假设给出能区别其他解释的预测。
5. 用最小实验逐个验证或排除假设，一次只改变一个变量并记录反证。
6. 找到根因后做最小修复。
7. 把最小复现转成回归测试；无法自动化时写明 seam 限制和手动验证步骤。
8. 完成前同时确认最小回归测试转绿、原始未缩减场景转绿；两者证明的范围不同，不能相互替代。
9. 清理临时日志、插桩和一次性诊断代码。

没有已实际运行且可重复判定红/绿的失败信号，不进入假设或修复阶段。

## 性能问题

1. 先建立 baseline：命令、数据量、环境、指标。
2. 找出瓶颈路径。
3. 一次只改一个变量。
4. 对比优化前后数据。
5. 如果优化引入复杂度，说明收益是否值得。

## 3-Strike Stop

满足任一条件时停止推进并上报：
- 连续 3 个假设失败。
- 修复触及超过 5 个文件且根因仍不清楚。
- 安全敏感路径无法验证。
- 性能测量不稳定且无法解释。

## Debug 清理

临时日志使用 `[DEBUG-xxxx]` 前缀。完成前用 PowerShell 搜索并清理：

```powershell
Get-ChildItem -Recurse -File | Select-String -Pattern '\[DEBUG-[A-Za-z0-9_-]+\]'
```
